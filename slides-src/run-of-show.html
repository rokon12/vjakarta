What a virtual thread is

Waiting gets cheap. Nothing gets faster.

  1. 05

    A platform thread is an OS thread 0:03

    Show what a waiting platform thread costs, so the audience sees what virtual threads change.

    click 0“A platform thread is a thin wrapper around an operating-system thread. One task takes one thread and keeps it until it finishes.”

    Point at one lane: the request on the left, its work drawn to the right.

    click 1“The solid part is real work. The hatched part is waiting for the database, and for a typical service that is most of the time. The thread is held the whole time.”

    Background. About a megabyte of stack is reserved per thread. The real cost is that OS threads are limited, so every server caps them.

    click 2“Because threads are expensive we pool them. In our service the pool is sixteen. Remember that number: it was quietly doing a second job.”

  2. 06

    A virtual thread belongs to the JVM 0:04

    Mount, park, unmount: the one mechanism the rest of the talk relies on.

    click 0“A virtual thread is a thread the JVM schedules itself. It needs an OS thread, its carrier, only while it is running.”

    click 1“When it blocks, on a socket, a sleep or a lock, the JVM parks it and the carrier picks up another one. Nobody holds an OS thread while waiting.”

    click 2“When the answer comes, it mounts again on whichever carrier is free. Your code is still plain blocking code.”

    click 3“So thousands can wait at once on a few carriers. The advice is: never pool virtual threads. Hold on to that advice. It is about to cost us.”

    Background. JEP 444, final since JDK 21.

  3. 07

    Nothing got faster 0:05

    The gain is throughput. No single request got faster.

    click 0“A measurement from my last talk, in plain Java: a thousand requests, each waits 100 ms. Top lane, a pool of 50. Bottom lane, a thread each.”

    click 1Let it play. “Fifty at a time on top. Everyone else queues for a thread.”

    click 2“2,084 milliseconds against 114. But every request still waited its 100 ms. Nothing got faster. We stopped queueing for a thread.”

Questions you may get

Short answers. The runs already made the argument.

Should I pool virtual threads?
No. Limit the dependency, not the threads: a budget per dependency, with maxAsync on its own executor, a semaphore, or @Bulkhead.
Does maxAsync with virtual = true make a thread pool?
No. It bounds how many tasks run at once. Each task still gets its own virtual thread.
Why not raise the pool to 200 connections?
Then the database is what saturates, and the limit moves again. Size the pool from what the database can take, then budget against it.
How do I pick the numbers?
Little’s law: in flight = throughput × time. About 360 charges a second × 52 ms ≈ 19 inside, so the door is 24.
What about Liberty’s request threads?
The resource returns a CompletionStage, so request threads are released. The limits are the door and the budgets.
Does cancel(true) work everywhere?
On Liberty’s managed CompletableFuture, yes. On a plain JDK CompletableFuture, no: use the Future from submit(), or structured concurrency.
And @Timeout?
It interrupts the call too, and like cancel it cannot un-send a charge. That is what the idempotency key is for.
Is synchronized safe now?
For pinning, yes, from JDK 24 (JEP 491). Native frames and class initializers still pin. The backup slide shows it.
Are the numbers repeatable?
Three runs each. At the big sale p99 on virtual threads ranged 2.3 to 3.7 seconds; the story held every time.
