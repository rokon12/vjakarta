# Demo App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A seat-reservation service on Open Liberty, in four tagged states (`before`, `switched`, `budgeted`, `deadlines`), that shows p99 exploding after the switch to virtual threads under a flash sale, and recovering once the limits are written down.

**Architecture:** One Jakarta EE WAR on Liberty. `POST /api/reservations` fans out seat holds (PostgreSQL, pool of 20) and one payment call (a separate plain-Java provider that answers 429 above its capacity) on a managed executor. k6 drives an open-model load with a flash sale; a small Python tool turns k6 output into the per-second p50/p99 series the deck will draw.

**Tech Stack:** Java 25, Open Liberty 26.0.0.11, liberty-maven-plugin 3.12.5, jakarta.jakartaee-api 11.0.0, MicroProfile Fault Tolerance 4.1, Metrics 5.1, Config 3.1, PostgreSQL 16 (Docker, `postgres:16-alpine`), driver 42.7.14, k6 1.6.1, Python 3.

**Spec:** `docs/superpowers/specs/2026-11-11-jakartaone-talk-design.md`

The deck gets its own plan after Task 7, when the measured numbers exist.

## Global Constraints

- The database pool is 20 connections. The `before` executor has `maxAsync = 16`. The `switched` diff on screen is one line.
- Every limit is one real services have. The only simulated latency is `pg_sleep` in the seat-hold query and the provider's sleep; both are said out loud on stage. No sleeps, locks or throttles anywhere else.
- Same k6 load, flash sale included, in every state. Open model only (arrival rate), never virtual users.
- Code looks written by a person: minimal comments, no banner or Javadoc headers, no defensive code the demo does not need, JDK 25 idioms. Plain-Java programs use instance `void main()` and `IO.println`.
- Ports: app 9080, provider 9095, PostgreSQL 5432 (container `vjakarta-db`).
- Commits are local. No push, no GitHub repo, no Pages, without the speaker's permission.
- Verification is by scripted runs and their printed output. The only unit test is for `tools/series.py`.

## Review Focus

- k6 runs out of VUs while the service is slow and silently drops arrivals, turning the open model into a closed one and hiding the explosion. `series.py` must report `dropped_iterations`, and every accepted run has 0 (Task 3 test, Task 4 check).
- A hidden concurrency cap (Liberty's request threads, the HTTP client's connection pool) masks the switch. The `in_flight` gauge must go well above 16 in `switched` (Task 4 check).
- `virtual = true` silently ignored by vendor configuration. Each state logs `isVirtual` once at the first task (Task 2, Task 4 check).
- Leftover state between runs (a growing `holds` table, a cold JIT) changes results. `./run.sh reset` truncates the table, the load starts with 10 s at the base rate, and Task 7 checks three runs per state agree.
- The laptop runs out of CPU, so latency comes from the machine, not the mechanism. Task 4 records CPU use of k6 and Liberty during the `switched` run.

### Task 2: The reservation endpoint in its `before` state

**Files:**
- Create in `src/main/java/ca/bazlur/tickets/`: `ReservationRequest.java`, `Reservation.java`, `ReservationResource.java`, `Reservations.java`, `SeatHolds.java`, `Payments.java`, `PaymentRefused.java`, `InFlight.java`
- Create: `src/main/resources/META-INF/microprofile-config.properties`

**Interfaces:**
- Consumes: `jdbc/tickets`, provider at `http://localhost:9095/charges`.
- Produces:
  - `TicketsApplication` carries `@ManagedExecutorDefinition(name = "java:app/concurrent/reservations", maxAsync = 16)`. This is the file the switch diff is shown on. (Liberty ignores resource definitions on a plain class, so it cannot live in a file of its own.)
  - `record ReservationRequest(int show, int seats)`, `record Reservation(UUID id, int seats)`.
  - `ReservationResource`: `@Path("/reservations")`, `@POST CompletionStage<Response> reserve(ReservationRequest request)` → 201 with the `Reservation`; a failed payment after retries → 503.
  - `Reservations.reserve(ReservationRequest) : CompletionStage<Reservation>`: for each seat, `executor.runAsync(() -> seatHolds.hold(...))`; one `executor.supplyAsync(() -> payments.charge(...))`; all in parallel, joined with `allOf`.
  - `SeatHolds.hold(UUID reservationId, int show, int seat)`: one connection, `insert into holds ...` and `select pg_sleep(?)` with `seat.query.millis` (default 10) from MP Config.
  - `Payments.charge(UUID reservationId, int cents)`: one shared Jakarta REST `Client`, POST to `payments.url`; 429 → `throw new PaymentRefused()`. Annotated `@Retry(retryOn = PaymentRefused.class)` and nothing more: the MicroProfile defaults (3 retries, no delay, 200 ms jitter).
  - `InFlight`: a `ContainerRequestFilter`/`ContainerResponseFilter` pair on `/reservations` counting requests in flight, exposed as the MP Metrics gauge `in_flight`.
  - Each run logs once, at the first task: `reservation tasks run on virtual threads: <true|false>`.

- [ ] **Step 1:** Write the files above.
- [ ] **Step 2:** Verify one request: `curl -s -X POST -H 'content-type: application/json' -d '{"show":1,"seats":4}' localhost:9080/api/reservations` returns 201 with an id; `psql` shows 4 rows in `holds` for it; the log line says `false`.
- [ ] **Step 3:** Verify metrics: `curl -s localhost:9080/metrics | grep -E 'in_flight|ft_retry|connectionpool'` shows the gauge, the retry counters and Liberty's connection-pool metrics (`waitTime`, `inUseTime`, managed/free connections). If the pool metrics are missing, enable the `monitor-1.0` feature and note it.
- [ ] **Step 4:** Commit: `add the reservation endpoint on a managed executor of 16`.

### Task 3: The flash-sale load and the series tool

**Files:**
- Create: `load/flash-sale.js`, `tools/series.py`, `tools/test_series.py`, `tools/fixtures/small.csv`
- Modify: `run.sh` (add `./run.sh load <name>`)

**Interfaces:**
- `flash-sale.js`: two scenarios, both `constant-arrival-rate`: `steady` at `BASE_RATE` (default 100/s) for `DURATION` (default 30s); `sale` at `SALE_RATE` (default 300/s, on top of steady) for `SALE_SECONDS` (default 3) starting at `SALE_AT` (default 10s). `preAllocatedVUs` 500, `maxVUs` 5000, request timeout 60s, body `{"show":1,"seats":SEATS}` (default 4).
- `./run.sh load <name>`: runs k6 with `K6_WEB_DASHBOARD=true`, `K6_WEB_DASHBOARD_EXPORT=results/<name>.html`, `--out csv=results/<name>.csv`, then `python3 tools/series.py results/<name>.csv`.
- `series.py <csv>`: prints one line per second of request start time (`second, requests, p50 ms, p99 ms, 201, 503, other`) and a summary line: `requests, p50, p99, on time (<= 500 ms), late, refused (503), errors, dropped_iterations`. Writes the same per-second rows to `<csv>.series.json` for the deck.

- [ ] **Step 1: Write the failing test.** `tools/fixtures/small.csv` holds k6 CSV rows for 10 requests (`http_req_duration` with `status` tags) across two seconds and one `dropped_iterations` row with value 2. `test_series.py`:

  - `test_p99_uses_nearest_rank`: for durations 10..100 ms in second 0, p99 = 100.
  - `test_summary_counts_status_and_drops`: on time, late, refused (503) and `dropped_iterations == 2` match the fixture.
- [ ] **Step 2:** Run `python3 -m unittest tools/test_series.py`. Expected: fails (no `series.py`).
- [ ] **Step 3:** Implement `series.py` with the standard library only. Bucket by request start: `timestamp - duration`.

### Task 5: `switched` and `budgeted`

**Files:**
- Modify: `TicketsApplication.java`, `Payments.java`, `Reservations.java`, `server.xml`
- Create: `src/main/java/ca/bazlur/tickets/Door.java`

**Interfaces:**
- `Door`: `ContainerRequestFilter`/`ContainerResponseFilter` on `/reservations` with a `Semaphore(door.limit)`; `tryAcquire` fails → abort with 503 and `Retry-After: 1`; release in the response filter. Counted as MP Metrics counter `door_refused`.
- Per-request fan-out limit `fanout.limit` (MP Config) on concurrent seat holds.
- `Payments.charge` gains `@Bulkhead(<provider limit>)`; `BulkheadException` is treated like `PaymentRefused`.
- `@Retry(maxRetries = 1, delay = 100, jitter = 50, retryOn = PaymentRefused.class)`.

- [ ] **Step 1:** Commit the one-line switch on `main`: `switch the reservation executor to virtual threads`. Tag `switched`. Run `./run.sh load switched` and confirm it matches the spike numbers.
- [ ] **Step 2:** One commit per fix, in this order, each with a run recorded in `docs/spike-results.md`: the door; `maxAsync` back as a budget (its value derived from the pool and the provider limit, with the arithmetic in the commit message); the fan-out limit; the bulkhead; the retry policy.
- [ ] **Step 3:** Check the spec's acceptance for `budgeted`: refusals only during the sale; p99 of admitted requests low throughout and normal as soon as the sale ends; more on time than both `before` and `switched`; no help from timeouts (the connection wait timeout is still the default). - [ ] **Step 4:** Tag `budgeted`.
